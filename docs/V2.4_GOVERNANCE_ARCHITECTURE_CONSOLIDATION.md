# DTEP v2.4 — Governance Architecture Consolidation

## 1. Research position

The prototype addresses a governance problem that remains after models, simulation runs, measurements, reports, and review records have been digitized: digital availability does not determine whether an item belongs to the current test case, whether its relationship is semantically valid, whether it is admissible as evidence, or whether it remains admissible after the source changes.

DTEP therefore treats governance as an executable transformation from a case-scoped ontology graph to admissible evidence and then to governed decisions.

The consolidated architecture is:

Objects → Typed Relations → Admissible Evidence → Governed Decisions

The central system claim is architectural: decision logic consumes only evidence that survives object scoping, relation-integrity checks, reuse authorization, applicability checks, and lifecycle invalidation.

## 2. Four-layer governance compiler

### 2.1 Object layer

DigitalTestCase(caseId) is the governance root. Test scenarios, events, measures, model assets, baselines, reports, deficiencies, evidence packages, and other artifacts are first-class ontology objects rather than implicit file attachments.

The object layer establishes stable identity and the boundary of the case being evaluated. A missing root or incompatible object type prevents downstream governance evaluation.

### 2.2 Relation layer

LinkEntry records determine how objects participate in the current case. Relation types and semantic roles encode governance meaning, including performance-test anchors, operational-evidence anchors, effectiveness measures, and formal digital-model review inputs.

The relation layer enforces four constraints:

1. the relation must point to the declared target object type;
2. governance roles must be legal for the relation;
3. one object cannot silently hold conflicting governance roles;
4. evidence owned by another case cannot enter the current case without an explicit reuse contract.

These constraints remove case-specific object identifiers from governance reasoning. Case variation is represented as ontology data.

### 2.3 Evidence layer

Objects connected by valid relations remain candidates until they pass evidence-admission rules.

Cross-case reuse requires an EvidenceReuseAuthorization matching the source case, target case, source object, relation, governance role, approved target task type, approval state, validity window, provenance, frozen source snapshot, and requalification boundaries.

A valid authorization permits bounded reuse. It does not transfer the source case's final judgment, expand VV&A scope, or increase the formal evidence grade.

Lifecycle invalidation is distinct from ontology corruption. Revocation, expiration, source-content drift, and source validation-domain drift move the reused evidence to a stale ledger. Stale evidence is excluded from trusted semantic-role buckets.

### 2.4 Decision layer

The decision layer evaluates lifecycle criteria using only admitted evidence. State-qualification, operational-test, and fielding-finalization actions are derived from criterion states and explicit authority prerequisites.

Evidence coverage remains descriptive. A high coverage percentage cannot cancel a blocking business prerequisite.

When admitted evidence becomes stale, the evidence is removed first. The affected criterion is recomputed from the remaining trusted evidence, and the existing action logic inherits the resulting blocker. No separate case-specific revocation branch is required.

## 3. Architecture-to-gate mapping

| Gate | Boundary exercised | Principal question | Result |
|---|---|---|---|
| v2.3.1 Second-Case Transportability | Object → Relation | Can a different task type use the same governance logic without case-specific branches? | CASE-01 and CASE-02 share one governance vocabulary and resolver |
| v2.3.2 Relation Completeness & Negative Transport | Relation → Evidence | Are malformed, conflicting, or foreign relations removed before evidence evaluation? | Type mismatch, cross-case pollution, illegal roles, and role conflicts fail closed |
| v2.3.3 Governed Cross-Case Evidence Reuse | Relation → Evidence | Under what conditions may foreign evidence be admitted? | Reuse requires bounded authorization, provenance, applicability, and bilateral approval |
| v2.3.4 Reuse Revocation & Change Propagation | Evidence → Decision | Does previously valid reused evidence stop influencing decisions when its basis changes? | Revocation, expiry, digest drift, and domain drift remove evidence and propagate blockers |

Together, the four gates test the interfaces between architecture layers rather than four unrelated features.

## 4. Runtime semantics

The governance API exposes a consolidated runtime view for each case:

- object count within the resolved governance scope;
- accepted and rejected relation counts;
- ontology hard-error count;
- number of trusted semantic-role evidence inputs;
- accepted and stale cross-case reuse counts;
- criterion count and blocking-criterion count;
- governed-action count and blocked-action count.

These metrics describe the state of the governance compiler. They are not qualification scores.

## 5. Fail-closed semantics

The consolidated architecture distinguishes three failure classes.

### Structural invalidity

Examples include a relation targeting the wrong object type, an illegal governance role, or a conflicting role assignment.

Structural invalidity is recorded in integrity.hardErrors. The affected relation never enters a trusted evidence bucket, and governed actions receive hard blockers.

### Evidence inadmissibility

Examples include cross-case reuse without an authorization, contract mismatch, lack of provenance, or a target task outside the approved reuse domain.

The evidence is rejected before decision criteria are evaluated.

### Evidence staleness

Examples include reuse-authorization revocation or expiration, source-object content change, and source validation-domain change.

Staleness is recorded separately from ontology corruption. The evidence is removed from the trusted set, dependent criteria are recomputed, and action blockers follow from the updated criteria.

## 6. Consolidated system story

The research narrative can be reduced to one problem and one mechanism.

**Problem.** A digital T&E platform can preserve data and provenance while still making an invalid governance inference if it cannot determine which evidence belongs to the current decision, under what semantic role it is admissible, and whether that admissibility survives change.

**Mechanism.** DTEP compiles a case-scoped object graph through typed relations and evidence-admission rules into governed decision criteria.

**Observable behavior.** The same governance logic operates across two different case types; malformed or foreign relations are rejected; explicitly authorized evidence can be reused; revoked, expired, or changed evidence automatically stops supporting downstream criteria.

**Boundary.** The current evidence supports architectural enforcement and traceable fail-closed behavior in synthetic/demo cases. It does not establish operational effectiveness, formal regulatory acceptance, or cross-organization external validity.

## 7. Paper claim–evidence structure

| Claim | Supporting evidence | Claim boundary |
|---|---|---|
| Governance logic can be separated from case-specific object identifiers | CASE-01/CASE-02 transportability gate and static source checks | Two synthetic cases, not population-level transportability |
| Typed ontology relations can prevent silent evidence contamination | Negative relation injections | Tested relation-failure classes, not every ontology defect |
| Cross-case evidence reuse can be bounded by explicit governance contracts | Authorization-backed reuse gate | Prototype authorization semantics, not an approved institutional procedure |
| Evidence validity can be revoked after source change and propagated to decisions | Revocation, expiry, digest-drift, and validation-domain-drift gate | Synchronous prototype evaluation, not distributed event propagation |
| Governed actions can remain explainable under evidence change | Criterion-to-action blocker propagation | Prototype lifecycle actions only |

## 9. Prototype presentation order

The governance workspace should present information in the following order:

1. four-layer governance compiler;
2. runtime counts at each layer;
3. v2.3.1–v2.3.4 boundary-validation evidence;
4. statutory/lifecycle criteria;
5. governed actions and blockers;
6. provenance, data-acceptance, and technical-state details.

This order exposes the research mechanism before implementation detail.

## 10. Consolidated architectural judgment

The v2.3.1–v2.3.4 results support treating DTEP governance as a four-layer compiler rather than as a collection of independent workflow rules. The strongest demonstrated property is not the number of modeled lifecycle functions. It is the preservation of decision admissibility under case transfer, malformed relations, bounded evidence reuse, and subsequent source change.

Further internal expansion of failure cases is unlikely to materially strengthen this architectural claim. The next empirical step should target an independent engineering context or organization-level workflow to test whether the same object–relation–evidence–decision contracts remain sufficient outside the two synthetic cases.
